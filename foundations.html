01 · Shared semantics

The basic exchange

Every version of HTTP gives a client and server a common way to describe a request and its result.

HTTP’s place in the web stack

A browser uses a URL to identify a resource, then sends an HTTP request to an origin server or intermediary. The response carries a status, metadata in header fields, and often a representation such as HTML, an image, or JSON. A page can trigger many exchanges as the browser loads styles, scripts, fonts, images, and API data.

HTTP is an application protocol. HTTP/1.1 and HTTP/2 commonly use TCP underneath. HTTP/3 maps the same broad semantics onto QUIC, which runs over UDP. HTTPS protects HTTP exchanges with TLS; QUIC integrates TLS 1.3 into its connection setup. See HTTP Semantics and HTTP/3.

Request and response structure

A request

A request identifies an action and target. It may include fields that describe client preferences, credentials, or message content.

GET /docs HTTP/1.1
Host: example.edu
Accept: text/html

A response

The server returns a status and fields. A response may include a representation or direct the client elsewhere.

HTTP/1.1 200 OK
Content-Type: text/html
Cache-Control: max-age=60

HTTP is stateless by design

HTTP does not require the server to remember an earlier request when it receives the next one. Applications build continuity with mechanisms such as cookies, session identifiers, tokens, or server-side data. Cookie scope and security attributes matter.

Methods and status codes

A method describes the request’s intended action. GET asks for a representation; POST sends content for processing; PUT and DELETE describe changes to a target. The status code summarizes the response: 2xx is success, 3xx redirects, 4xx reports a client-side problem, and 5xx reports a server-side failure. Current definitions are in RFC 9110.
