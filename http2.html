03 · A protocol redesign

HTTP/2: more exchanges on one connection

HTTP/2 changed how messages travel across the network while preserving the HTTP meanings applications use.

One connection, many streams

HTTP/2 represents messages with binary frames. Frames from multiple streams can be interleaved on one TCP connection, so a browser and server can handle concurrent exchanges. RFC 9113 describes it as an optimized expression of HTTP semantics.

01

Binary framing

Frames carry message parts and control information in a format meant for parsing rather than direct reading.

02

Multiplexing

Several streams can make progress on one connection, reducing the need for many connections to the same origin.

03

HPACK

Header compression reduces repeated field bytes. HPACK is specified in RFC 7541.

The important boundary

HTTP/2 still uses TCP

Multiplexing separates HTTP exchanges into streams, but TCP presents one ordered byte stream to HTTP/2. If a TCP packet is lost, later bytes cannot be delivered to the application until recovery. This can temporarily hold up multiple HTTP/2 streams on that connection. HTTP/3’s use of QUIC changes this transport behavior.

What stays the same?

Developers still work with URLs, methods, status codes, header fields, caching, and content types. The network representation changes; the application-level model remains recognizable. A browser Network panel can show the negotiated protocol alongside request and response details.

HTTP/2 improves how exchanges share a connection, but does not guarantee a faster result for every site. Server configuration, latency, payload size, congestion, and client support all affect performance.
